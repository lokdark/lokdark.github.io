> **一句话结论**：Skill 是**程序性知识包**（何时用 + 怎么做 + 怎么校验），靠**渐进披露**做到"技能很多、上下文只涨一点"；真正难的不是写 `SKILL.md`，而是**检索路由、生命周期管理、用外部信号迭代**。

## 一、概论

先从最容易被混淆的地方说起：**Skill 不是 Tool**。

- **Tool 是原子的能力**：读一个文件、跑一次 SQL、调一次 HTTP，算完就结束。
- **Skill 是一个文件夹 + 一份 `SKILL.md`**：封装了"什么场景该用、按什么步骤做、产出长什么样、怎么校验"的程序性知识[1][2]。

举个具体的例子：同样是"给一张 PDF 表单填数"，Tool 只能提供「读取 PDF」「写文本域」两个动作，而一个 Skill 会告诉你：先解析出表单字段名 → 再按字段类型（文本/日期/复选框）决定写法 → 填完重新渲染校验 → 输出填写报告。**这部分知识以前只能塞在系统提示里，现在被拆出来、可按需加载、可版本化。**

第二个关键点是**技术支点：渐进披露（progressive disclosure）**。启动时只加载每个技能的 `name` + `description`（约 100 tokens/个），命中任务才读正文，需要时再读 `references/`、`scripts/`、`assets/`[1][2][8]。所以技能数量可以很多，而上下文只涨一点点。

学习重点不只是"怎么写 `SKILL.md`"，还要关注下述问题：

1. **技能检索与路由**——怎么在几百个技能里选出该用的那个（以及该不用的那个）
2. **生命周期管理**——版本、冲突、退场
3. **用外部反馈而非自反馈来迭代**——模型自己给技能打分会越改越偏[5][6][7]

## 二、基础概念

| 概念 | 本质 | 粒度 | 上下文成本 | 能否跨平台搬运 | 典型载体 |
| --- | --- | --- | --- | --- | --- |
| Prompt | 一次性文本指令 | 最小 | 每次全量进上下文 | 手工复制 | 对话输入 |
| Tool / Tool Calling | 一个原子函数（读文件、跑 SQL、调 HTTP） | 单动作 | schema 常驻 | 靠 MCP 互通 | JSON Schema 函数 |
| **Skill** | **程序性知识包：何时用 + 怎么做 + 校验** | 一段工作流 | 渐进加载 | **是，`SKILL.md` 为标准格式** | 文件夹 + `SKILL.md` |
| MCP Server | 工具/数据的接入协议 | 能力供给层 | 按需连接 | 是 | MCP server |
| Agent | 规划 + 记忆 + 工具/技能调度 | 系统 | 最高 | 否 | LangGraph / SDK |

容易混淆的点：

**1.Skill 与 MCP：不是替代，而是分工。** MCP 是工具层的通信协议，负责"能发现什么工具、能调什么 API、能读写什么数据"——扩展的是 Agent 的**行动半径**；Skill 是知识封装，负责"面对这类任务该按什么流程走、先调谁后调谁"——提供的是**操作手册**。官方参考架构也体现了这层分工：**Agent 配置（技能 + MCP Server）+ Agent 虚拟机（文件系统 + bash/python）**[1]，一个对外、一个对内、一个提供执行环境。

**2.Skill 不是长 Prompt。** 长 Prompt 无法按需加载、无法带脚本、无法被检索、无法复用；Skill 的正文建议控制在 5000 tokens 以内，超额部分拆到 `references/`[8]。

**3.Skill 不是 Subagent。** Skill 是"知识 + 步骤"，不引入独立推理进程；需要隔离上下文、并行执行时才用子代理。

> 顺带厘清一个高频混淆：Skill、RAG、微调，分别解决什么问题：简单来说，RAG 解决"事实不在模型里"的问题——它把外部知识检索出来塞进上下文；微调解决"行为要内化到权重"的问题——用标注数据让模型学会某种输出风格或领域知识；Skill 解决"流程性知识怎么按需注入"的问题——它不改权重、也不做向量检索，只是一份被检索并按需展开的说明书。

## 三、规范解剖

### 3.1 目录结构

```
my-skill/
├── SKILL.md          # 必需：YAML 元数据 + Markdown 指令
├── scripts/          # 可选：可执行脚本（确定性步骤交给代码，不交给模型即兴发挥）
├── references/       # 可选：规范条文、API 文档、长表格，按需读
├── assets/           # 可选：模板、schema、样例输入输出
└── ...               # 其它任意文件
```

### 3.2 `SKILL.md` 元数据硬约束[2]

| 字段 | 约束 |
| --- | --- |
| `name` | 必填；≤64 字符；仅小写字母/数字/连字符；不得含 XML 标签；不得含保留词（如 `anthropic`、`claude`） |
| `description` | 必填非空；≤1024 字符；**这是唯一决定"会不会被触发"的字段** |
| 正文 | 建议 < 5000 tokens，写清触发条件、步骤、产出格式、失败处理、校验清单 |

> 工程要点：`description` 是**检索键**。要写"做什么 + 什么条件下用 + 不适用什么"，因为路由模型只看得到它。

### 3.3 渐进式披露（Skill 能规模化利用的核心）[1][2]

![三级渐进式披露](/images/posts/agent-skills-notes/01-progressive-disclosure.png)

| 级别 | 加载内容 | 何时 | 上下文预算 |
| --- | --- | --- | --- |
| L1 发现 | 只 `name` + `description` | 启动时常驻 | 约 100 tokens/技能 |
| L2 激活 | 完整 `SKILL.md` 正文 | 任务与描述匹配时 | 建议 < 5000 tokens |
| L3 执行 | `scripts/` 实跑、`references/`、`assets/` 读取 | 正文指明需要时 | 按需、近似无界 |

注：技能库可以很大，但每个技能都必须能被一句话说清用途——因为 Agent 的匹配机制依赖语义密度，而非信息堆砌。这也与 SkillsBench 的观察一致：聚焦 2–3 个具体场景的技能，命中精度和实际效果都优于覆盖全场景的大文档[4]。

### 3.4 安全边界（比功能更先设计）[3]

- 第三方技能 = **第三方代码 + 第三方指令**，权限必须在技能之外授予（工具授权不与技能绑定）；
- 锁定技能版本（pin revision）、人工审查 `scripts/`、审查指令里是否有"忽略上层约束"一类的越权话术；
- 技能目录里的一切都是**待执行的输入**，不是可信配置。

### 3.5 最小可用模板

```markdown
---
name: kv-cache-scheduler-audit
description: 审计 vLLM 的 KV Cache 与调度器配置是否与目标负载匹配。当用户给出显存规格、
             并发目标或出现 OOM/吞吐不达预期时使用；不适用于纯代码风格审查。
---

# KV Cache / Scheduler 配置审计

## 触发条件
- 存在 `gpu_memory_utilization`、`max_num_seqs`、`block_size` 等配置；
- 症状为 OOM、preemption 频繁、或吞吐低于目标。

## 步骤
1. 抽取配置与硬件规格 → 写入 `assets/inventory.yaml` 模板。
2. 按 `scripts/estimate.py` 计算 KV 池块数与理论并发上限（**不要让模型口算**）。
3. 对照 `references/thresholds.md` 判断是否落在合理区间。
4. 输出结论表格：瓶颈项 / 依据 / 建议值 / 风险。

## 产出格式
Markdown 表格 + 一段 ≤5 行的结论；不输出完整日志。

## 失败处理
- 缺显存规格：明确列出缺失字段并停止。
- 脚本报错：贴出错误原文，不擅自改配置。

## 校验清单
- 每个结论都有配置项或计算值支撑
- 建议值与硬件约束不矛盾
```

### 3.6 `description` 怎么写：正例与反例

既然触发完全由 `description` 决定，它就值得反复打磨。经验上它应该同时回答三个问题：**做什么、什么时候用、什么时候别用**。

```yaml
# 反例：功能广告，没有触发条件，路由模型无从判断
description: 一个强大的数据分析技能，能处理各种复杂的数据任务。

# 正例：动作 + 触发场景 + 排除条件
description: 对 CSV/Parquet 做探索性分析并输出结论表。当用户给出数据文件、
             问"这批数据有没有异常/趋势"或需要选型图表时使用；
             不适用于实时流计算或需要写回生产库的场景。
```

另外两个细节：

- **不要用没有信息量的词开头**（如"强大的…""智能的…"），它们占字符但不提供检索信号；
- **把领域关键词放进去**（文件名类型、工具名、症状词），因为路由多半是语义 + 关键词混合匹配。

### 3.7 什么时候该写脚本

一条实用的判断：**凡是"Agent调工具+读结果"就能确定完成的步骤，都交给 `scripts/`**。数值计算、格式转换、正则校验、批量改名都属于这类；而需要模糊判断、语义理解、创意生成的留给模型做。脚本的好处不只是准确，还有可复现、可测试、可断言——校验清单里可以直接引用脚本的退出码。

## 四、机制层：技能生命周期

真实的系统不是一个 `SKILL.md`，而是一条链。每一环都有已知的坑：

![技能生命周期](/images/posts/agent-skills-notes/02-skill-lifecycle.png)

| 阶段 | 关键动作 | 已知失败模式 |
| --- | --- | --- |
| Authoring 编写 | 人写 / 轨迹蒸馏 | 模型自写技能平均无效甚至负收益[4]；自反馈多轮会**递归漂移**[5] |
| Registry 注册 | 命名、版本、标签、依赖声明 | 无版本 → 不可复现；改名 → 路由失效 |
| Retrieval 检索 | 语义召回 + 关键词 + 领域过滤 | 库越大检索精度越低（**library drift**）[7] |
| Routing 路由 | 决定"用哪个 / 不用" | 过度触发比不触发更伤：注入错误指引会污染后续每一步 |
| Composition 编排 | 多技能串联、依赖、并行、重试 | 缺少中间校验点，一处错全链错 |
| Execution 执行 | 沙箱、超时、权限最小化 | 脚本副作用不可逆 |
| Evaluation 评估 | 三层：技能质量 / 轨迹对齐 / 任务结果[5] | 只看最终分数 → 学不到"哪一步错了" |
| Retirement 退役 | 淘汰低命中、过期、冲突技能 | 不淘汰 = 静默退化，指标缓降而无报错[7] |

### 4.1 一次调用的完整时序

把这八环落到一次真实请求上，大概是这个样子：

1. **启动**：每个技能的 `name` + `description` 进入路由可用的索引（或直接注入系统提示）；
2. **请求到达**：路由层用语义相似度 + 关键词 + 领域过滤粗排，得到候选；
3. **判定**：命中就加载完整 `SKILL.md`（L2）；没命中就走通用流程，**不要为了"用上技能"而硬套**；
4. **执行**：按正文步骤调工具、跑脚本，需要细则时才读 `references/`（L3）；
5. **校验**：跑正文里的校验清单/脚本断言，不通过就按"失败处理"分支走；
6. **留痕**：把这次轨迹（用了哪个技能、跳了哪步、失败在哪）存下来——它是后续修订与评估的唯一原料；
7. **回流**：低命中、高失败率、与新版工具冲突的技能进入退役评审。

注：其中第 6 步容易被省掉，但这是最影响长期效果的，这是后续优化正确率的关键。

### 4.2 评估分层

单看端到端成功率会掩盖问题，实践中至少分三层：

| 层 | 看什么 | 怎么拿到信号 |
| --- | --- | --- |
| 技能质量 | `description` 是否含触发条件、步骤是否可执行、有没有校验清单 | 静态审查 + 人工抽样 |
| 轨迹对齐 | 该用技能时用了吗、步骤有没有跳、工具调用顺序对不对 | 轨迹打分（可规则化、可人工） |
| 任务结果 | 端到端成功率、token/时延成本、返工率 | 测试集 + 线上反馈 |

关键原则：**必须有一个外部信号**（测试用例、人工验收、线上指标），模型自评只能当辅助。自反馈多轮迭代会递归漂移[5]，技能库越大越明显[7]。

## 五、SKILL设计注意点
1. 写可执行步骤，不写知识摘要
Skill 的价值在于告诉 Agent「怎么做」，而不是「是什么」。把背景资料、概念解释塞进 SKILL.md，只会稀释核心指令的权重。如果确实需要参考资料，用独立文件存放，在正文中用路径引用。

2. Description 要写触发条件，不是功能广告
description 字段是 Agent 做技能匹配的检索入口。写「用户生成季度报表时触发」比写「强大的报表生成工具」有效得多。没有触发条件的description，Agent永远找不到它。

3. 正文控制在合理长度
SKILL.md 每次命中都会被注入上下文窗口。正文超过 5000 tokens 时，单次加载就会吃掉大量推理预算，挤压真正的思考空间。建议核心流程控制在 2000 tokens 以内，细节拆到 scripts/ 或 references/ 子目录里按需读取。

4. 数值计算交给脚本，不让模型算
模型做算术的可靠性远低于确定性程序。凡是涉及金额、日期差、统计聚合等数值类任务，一律写成 scripts/ 下的 Python 或 Shell 脚本，由 Agent 调用。

5. 技能数量不是越多越好
实测表明，技能库膨胀到一定规模后，检索精度下降带来的噪声会抵消技能本身的收益，最终效果甚至低于不装任何技能的基线。建议定期清理低命中率技能。

6. 验收必须有外部信号，不自评自测
让模型对技能输出打分的做法会导致递归漂移——模型倾向于给自己的产物打高分，错误被层层放大。验收应引入外部校验：单元测试、人工抽检、或者与已知正确结果的自动比对。

7. 工具权限在技能之外授予
Skill 文件里不应该出现 API Key、token、权限声明。权限应由 Agent 宿主环境统一管控。把权限写进技能里，任何能读到该技能的人都能拿到，这是一个比较危险的行为。

8. 版本固定，保证可复现
Skill 依赖的脚本、工具版本、模型行为都可能随时间变化。SKILL.md 中应声明依赖版本（或在配套 metadata.json 中锁定），确保同一技能在不同时间、不同环境下跑出一致结果。

9. 建立技能退役机制
工具升级、API 弃用、模型版本迭代都会让旧技能静默退化。没有主动退役机制的技能库会随时间积累「僵尸技能」——不报错但产出错误结果。建议为每个技能设置最后验证日期，超过阈值自动标记待审查。

10. 评估触发成本
每次技能命中都会占用上下文预算。高频触发的技能如果内容冗长，会持续压缩留给真正推理的 token 空间。设计时应权衡这个技能的上下文开销？高频技能可以考虑内容精简一点，低频技能可以考虑懒加载或按需展开。
